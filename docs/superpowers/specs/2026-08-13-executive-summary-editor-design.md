# Executive Summary 편집·공개·이력 설계

## 1. 문서 상태

- 날짜: 2026-08-13
- 대상: MI Intelligence Portal의 localhost·LAN 배포
- 상태: 대화에서 승인된 설계, 구현 전 최종 문서 검토 대기
- 배포 경계: GitHub Pages는 사용하지 않는다. 한 대의 서버 PC가 HTTP로 정적 대시보드와 편집 API를 제공하고 같은 LAN의 사용자가 접속한다.

## 2. 목표

1. 일반 LAN 사용자는 로그인 없이 대시보드 데이터를 조회한다.
2. 편집자는 이름과 공용 비밀번호로 전역 편집 모드에 들어간다.
3. 모든 페이지의 Executive Summary를 현재 카드 안에서 직접 편집한다.
4. 편집 내용은 자동 생성본과 사용자 수정본을 구분하고, 검토와 공개 상태를 별도로 관리한다.
5. 일반 사용자는 마지막으로 공개된 내용만 본다.
6. 원본 데이터가 바뀌면 관련 페이지의 편집 상태만 새 자동 생성본으로 초기화한다.
7. 편집자는 누가 언제 무엇을 바꿨는지 선형 버전 이력과 변경 전후 비교로 확인하고 과거 버전을 복원할 수 있다.
8. 콘텐츠는 로컬 JSON, 이력은 로컬 JSONL로 보존하며 런타임 파일은 Git에서 제외한다.

## 3. 제외 범위

- HTTPS와 외부 인터넷 배포
- 사용자별 계정과 신원이 확인된 감사 체계
- 실제 Git 브랜치처럼 여러 수정안을 분기·병합하는 기능
- 일반 조회자에게 편집자 이름이나 변경 이력을 공개하는 기능
- Executive Summary 외의 차트 수치, 페이지 제목, 부제, 기준일 편집
- Weekly Sell-through의 YoY·WoW 수치 편집
- 서식 있는 문서 편집기와 HTML 입력
- 런타임 편집 내용을 자동으로 Git 커밋하거나 푸시하는 기능

편집자 이름은 본인이 직접 입력하므로 변경 이력은 작업 기록이며 신원 증명이 아니다. HTTP에서는 같은 LAN의 공격자가 비밀번호나 세션을 가로챌 수 있다는 위험을 수용한다.

## 4. 시스템 구조

한 Python 프로세스가 정적 파일과 같은 출처의 API를 함께 제공한다.

```text
LAN 브라우저
 ├─ 일반 조회 ──────────────┐
 └─ 이름 + 공용 비밀번호 ──┤
                            ▼
                     Python 로컬 서버
                     ├─ site/ 정적 파일
                     ├─ 공개 콘텐츠 API
                     ├─ 인증된 편집 API
                     ├─ JSON 콘텐츠 저장소
                     ├─ JSONL 버전 이력
                     └─ 메모리 세션
```

서버만 로컬 콘텐츠 파일을 읽고 쓴다. 공개 API는 공개 스냅샷만 반환한다. 자동 생성본, 비공개 작업본, 이력은 인증된 편집 API에서만 반환한다. React 정적 번들에는 미공개 요약 문구를 포함하지 않는다.

Python 서버 내부는 다음 세 책임으로 분리한다.

- 정적·API 라우팅: 요청을 공개 조회, 편집, 인증, 정적 파일로 분기한다.
- 인증·세션: 비밀번호 검증, 로그인 제한, 세션과 CSRF 토큰을 관리한다.
- 편집 저장소: 검증, 버전 충돌, JSON 교체, JSONL 추가, 복구를 담당한다.

외부 패키지는 추가하지 않고 Python 표준 라이브러리를 사용한다.

자동 생성은 같은 입력에서 항상 같은 결과를 내는 순수 계산이어야 한다. 숫자 반올림과 문장 형식은 각 화면의 현재 데이터 표기 규칙을 따른다.

Weekly Sell-through에는 별도 Executive Summary 카드를 추가하지 않는다. 일반 사용자는 공개된 세부 내용이 없으면 지역·YoY·WoW 열만 보고 `세부 내용` 열은 보지 않는다. 편집 모드에서는 세부 내용 열이 항상 나타나며 YoY·WoW는 읽기 전용이다. 공개 여부는 지역별이 아니라 표 전체를 한 단위로 관리한다.

## 6. 기본값과 데이터 변경 감지

빌드 전에 페이지별 기본 콘텐츠 생성기가 정규화된 관련 데이터와 자동 생성 문구를 만든다. 생성 스크립트는 다음 정보를 서버만 읽는 기본값 JSON에 기록한다.

```json
{
  "schemaVersion": 1,
  "pages": {
    "sigma": {
      "kind": "bullets",
      "dataRevision": "sha256:...",
      "content": ["..."]
    }
  }
}
```

`dataRevision`은 소스 파일의 공백이나 코드 서식이 아니라 자동 생성에 실제로 사용한 정규화 데이터의 안정적인 JSON 표현을 SHA-256으로 계산한다. 공통 데이터가 바뀌어 여러 페이지가 영향을 받으면 해당 페이지들의 revision이 각각 바뀐다.

기본값 JSON은 저장소 루트의 `editorial-defaults.json`에 생성하며 React가 가져오지 않는다. 이 파일은 `site/` 밖의 추적되는 데이터 빌드 산출물로, 데이터 변경과 함께 다시 생성·커밋한다. 따라서 새 체크아웃에서도 Node 실행 없이 Python 서버가 시작할 수 있다. 런타임 편집 JSON만 Git에서 제외한다.

서버는 시작할 때와 각 편집·공개 API 요청 전에 기본값 파일의 수정 시각을 확인한다. 파일이 바뀌었을 때만 다시 읽어 페이지별 revision을 비교한다.

- revision이 같으면 작업본과 공개본을 유지한다.
- revision이 바뀌면 해당 페이지만 새 자동 생성본, 미검토, 비공개로 초기화한다.
- 초기화 전에 기존 작업본과 공개본을 `data_reset` 시스템 이력에 전체 스냅샷으로 남긴다.
- 데이터 초기화에서는 오래된 공개본을 즉시 숨긴다.
- 처음 도입할 때 현재 요약은 모두 자동 생성본, 미검토, 비공개로 등록한다.

## 7. 콘텐츠 상태 모델

현재 상태 JSON은 페이지별 작업본과 마지막 공개본을 분리한다.

```json
{
  "schemaVersion": 1,
  "pages": {
    "sigma": {
      "kind": "bullets",
      "dataRevision": "sha256:...",
      "version": 12,
      "draft": {
        "mode": "default",
        "customContent": null,
        "reviewed": false,
        "updatedAt": "2026-08-13T00:00:00Z",
        "updatedBy": "system"
      },
      "published": {
        "sourceVersion": 11,
        "content": ["마지막 공개 문구"],
        "publishedAt": "2026-08-12T02:00:00Z",
        "publishedBy": "김지은"
      }
    }
  }
}
```

`draft.mode`는 편집자가 선택하는 `default` 또는 `custom`이다.

- `default`: 현재 기본값 JSON의 자동 생성본을 작업본으로 사용하고 `customContent`는 `null`이다.
- `custom`: 편집자가 입력한 내용을 `customContent`에 저장한다.
- 문구 입력을 시작하면 UI가 `custom`으로 전환한다.
- `자동 생성본으로 복원`을 누르면 확인 후 `default`로 전환한다.
- 자동 생성본도 검토 완료 후 공개할 수 있다.

상태 전이 규칙:

1. 콘텐츠나 모드를 바꾸어 저장하면 `reviewed`는 자동으로 `false`가 된다.
2. 검토 완료는 현재 버전에만 적용한다.
3. 공개는 검토 완료된 현재 작업본에서만 가능하다.
4. 공개하면 해석된 전체 콘텐츠를 `published`에 복사한다.
5. 공개된 작업본을 다시 수정해도 일반 사용자는 이전 `published`를 계속 본다.
6. 공개 취소는 현재 공개본을 숨기지만 작업본과 이력은 유지한다.
7. 데이터 revision 변경은 작업본을 기본값으로 초기화하고 공개본도 숨긴다.
8. 과거 버전 복원은 현재 공개본을 바꾸지 않고 새 미검토 사용자 수정본을 만든다.

## 8. 편집 화면

### 8.1 전역 편집 모드

페이지 상단에 `편집 모드` 버튼을 둔다. 로그인 창에는 편집자 이름과 공용 비밀번호가 필요하다. 성공하면 상단에 `편집 중: 이름`, `로그아웃`을 표시한다. 편집 모드는 브라우저 세션 동안 모든 페이지에 적용된다.

일반 조회자는 다음만 본다.

- 공개 스냅샷이 있으면 Executive Summary 카드
- 공개 스냅샷이 없으면 카드 자체를 숨김
- Weekly Sell-through는 공개 상세가 없으면 세부 내용 열을 숨김

편집자는 비공개 작업본도 모두 본다.

### 8.2 카드 안에서 바로 편집

승인된 방식은 별도 오른쪽 패널이 아니라 Executive Summary 카드가 입력 화면으로 직접 전환되는 방식이다.

카드 읽기 상태에는 다음을 표시한다.

- `자동 생성` 또는 `사용자 수정`
- `미검토` 또는 `검토 완료`
- `비공개` 또는 `공개`
- `편집`, `변경 이력`

`편집`을 누르면 같은 카드 안에서 콘텐츠 형식에 맞는 입력창을 표시한다. 동작은 `자동 생성본으로 복원`, `취소`, `작업본 저장`, `검토 완료`, `공개`, `공개 취소`로 분리한다. 저장과 공개를 한 버튼으로 합치지 않아 실수로 공개되는 것을 막는다.

- 일반 페이지: 불릿 입력 1~3개, 순서 변경, 추가, 삭제
- MI Insight Weekly Report: 소제목과 그 아래 세부 문장 편집
- Weekly Sell-through: 각 지역의 세부 내용 셀만 입력창으로 변경

입력 중 페이지를 떠나거나 로그아웃하면 저장하지 않은 변경이 있다는 확인을 표시한다.

## 9. 선형 버전 이력

각 상태 변경은 `history.jsonl`에 전체 전후 스냅샷을 한 줄로 추가한다. 콘텐츠 크기가 작으므로 diff만 저장하는 방식보다 복구가 단순하다.

```json
{
  "eventId": "...",
  "page": "sigma",
  "version": 13,
  "parentVersion": 12,
  "action": "save",
  "editor": { "name": "김지은", "ip": "192.168.0.15" },
  "timestamp": "2026-08-13T00:00:00Z",
  "before": { "...": "전체 이전 상태" },
  "after": { "...": "전체 이후 상태" },
  "restoredFromVersion": null
}
```

행동은 `initialize`, `save`, `mark_reviewed`, `mark_unreviewed`, `publish`, `unpublish`, `data_reset`, `restore` 중 하나다. 시스템 초기화에는 편집자 이름을 `system`으로 기록하고 IP는 비운다.

편집 모드의 `변경 이력` 창은 최신순 선형 목록을 보여준다.

- 버전, 편집자, 시각, 행동
- 선택한 버전의 전체 내용
- 앞 버전과의 문장 단위 변경 전후 비교
- 버전 두 개를 선택한 비교
- 과거 버전을 현재 작업본으로 복원

복원은 과거 기록을 수정하지 않는다. 현재 버전의 다음 번호로 `restore` 이력을 만들고 `restoredFromVersion`을 기록한다. 복원본은 현재 데이터와 다를 수 있으므로 항상 사용자 수정본, 미검토로 시작한다.

IP는 JSONL에는 남기지만 UI 응답과 화면에서는 제외한다. 변경 이력 API는 편집 세션에만 공개한다.

## 10. 인증과 세션

### 10.1 최초 설정과 비밀번호 변경

- 인증 파일이 없으면 편집 기능은 설정 대기 상태다.
- 최초 공용 비밀번호 설정은 원격 주소가 `127.0.0.1` 또는 `::1`인 요청만 허용한다.
- 이후 비밀번호 변경도 유효한 편집 세션과 loopback 요청을 모두 요구한다.
- LAN 사용자는 조회와 로그인만 가능하고 비밀번호 설정·변경은 할 수 없다.
- 비밀번호는 10~128자로 제한한다.
- Python `hashlib.scrypt`와 무작위 salt로 해시하며 원문을 저장하거나 기록하지 않는다.

### 10.2 로그인과 세션

- 편집자 이름은 앞뒤 공백을 제거한 1~40자 일반 문자열이다.
- 서버가 256비트 무작위 세션 토큰과 별도 CSRF 토큰을 만든다.
- 세션 토큰은 `HttpOnly`, `SameSite=Strict`, `Path=/`인 세션 쿠키로 전달한다.
- HTTP이므로 `Secure` 속성은 사용할 수 없다.
- 세션은 메모리에만 두며 브라우저 종료, 로그아웃, 서버 재시작 또는 8시간 미사용으로 만료한다.
- 세션 쿠키의 토큰을 파일이나 로그에 기록하지 않는다.
- 같은 출처의 상태 변경 요청은 CSRF 토큰을 사용자 지정 헤더로 보내야 한다.
- CORS는 허용하지 않고 `Origin`과 `Host`를 확인한다.

IP별 최근 10분 로그인 실패가 5회가 되면 남은 창 동안 `429`를 반환한다. 로그인 성공 시 해당 IP의 실패 기록을 지운다. IP는 전달 헤더가 아니라 실제 소켓 주소를 사용한다.

## 11. API 경계

모든 응답은 JSON이며 정적 사이트와 같은 출처에서 제공한다.

### 공개

- `GET /api/editorial/pages/{page}`: 공개 스냅샷만 반환한다. 공개본이 없으면 `published: null`을 반환한다.

### 설정·세션

- `GET /api/editor/session`: 현재 편집 세션과 최초 설정 필요 여부
- `POST /api/editor/setup`: loopback 전용 최초 비밀번호 설정
- `POST /api/editor/login`: 이름과 공용 비밀번호 로그인
- `POST /api/editor/logout`: 현재 세션 종료
- `PUT /api/editor/password`: loopback과 인증을 모두 요구하는 비밀번호 변경

### 인증된 편집

- `GET /api/editor/pages/{page}`: 기본값, 작업본, 공개본, 상태, 현재 버전
- `PUT /api/editor/pages/{page}/draft`: 작업본 콘텐츠나 모드 저장
- `POST /api/editor/pages/{page}/review`: 검토 완료 또는 해제
- `POST /api/editor/pages/{page}/publish`: 현재 검토 완료 작업본 공개
- `POST /api/editor/pages/{page}/unpublish`: 공개 취소
- `GET /api/editor/pages/{page}/history`: IP가 제거된 버전 목록
- `GET /api/editor/pages/{page}/history/{version}`: IP가 제거된 전체 버전과 diff 입력
- `POST /api/editor/pages/{page}/restore`: 과거 버전을 새 작업본으로 복원

모든 상태 변경은 클라이언트가 본 `expectedVersion`을 요구한다. 현재 버전과 다르면 저장하지 않고 `409`와 최신 버전·수정자·수정 시각을 반환한다.

요청 본문은 64 KiB로 제한한다. 서버는 페이지 키, 콘텐츠 종류, 고정 지역 키, 배열 개수, 문자열 길이, 빈 문장을 다시 검증한다. 일반 불릿과 세부 문장은 각각 1~500자, 소제목은 1~100자로 제한한다. Weekly Sell-through 지역 세부 문장은 비어 있을 수 있지만 공개 시 적어도 한 지역에 한 문장이 있어야 한다.

## 12. 동시 편집과 오류 처리

Python `ThreadingHTTPServer`의 여러 요청이 동시에 들어오므로 모든 콘텐츠 변경은 하나의 저장소 잠금 안에서 처리한다.

1. 인증, CSRF, 입력, `expectedVersion`을 검증한다.
2. 다음 전체 상태와 전체 이력 이벤트를 메모리에서 만든다.
3. 이력 한 줄을 추가하고 flush와 fsync를 완료한다.
4. 기존 `content.json`을 `content.json.bak`으로 보존한다.
5. 새 콘텐츠를 같은 디렉터리의 임시 파일에 쓰고 fsync한 뒤 `os.replace`로 교체한다.

이력은 전체 스냅샷을 가지므로 서버 시작 시 마지막 정상 이력의 버전이 콘텐츠보다 앞서면 마지막 이력의 `after`로 콘텐츠를 다시 만든다. JSONL 마지막 줄이 중간에 끊겼으면 마지막 완전한 JSON 줄까지만 정상 이력으로 사용하고 손상된 꼬리는 별도 복구 파일로 옮긴다.

이력 기록 뒤 콘텐츠 교체가 실패하면 같은 `after` 스냅샷으로 콘텐츠 복구를 즉시 한 번 시도한다. 그래도 실패하면 추가 변경을 받지 않고 편집 API를 읽기 전용으로 전환한다.

- `content.json`만 손상되면 `.bak` 또는 마지막 정상 이력으로 복원한다.
- 현재 파일, 백업, 정상 이력이 모두 없으면 덮어쓰지 않고 편집 API를 읽기 전용으로 전환한다.
- 복구와 읽기 전용 전환은 서버 콘솔과 편집 모드 경고에 표시한다.
- API 장애가 나도 정적 대시보드와 일반 데이터는 계속 보이며 편집 콘텐츠만 숨긴다.
- `409` 충돌 시 UI는 사용자 초안을 보존하고 최신 작업본과 나란히 보여준다. 자동 병합은 하지 않으며 사용자가 최신본을 불러오거나 자기 초안을 복사해 다시 적용한다.

## 13. 로컬 파일과 백업

```text
editorial-defaults.json
runtime/editorial/
├─ content.json
├─ content.json.bak
├─ history.jsonl
└─ auth.json
```

`editorial-defaults.json`은 빌드가 재현하는 서버 전용 기본값 manifest다. `runtime/` 전체를 `.gitignore`에 추가한다. 콘텐츠 변경 때마다 직전 정상 `content.json`을 자동 보존하고 JSONL 전체 스냅샷으로 모든 버전을 복구할 수 있게 한다. 런타임 편집은 Git 상태를 바꾸지 않는다.

자동 생성 기본값과 revision 산출물은 런타임 비밀번호·이력과 분리한다. 서버가 읽을 수 있지만 `site/` 아래에는 두지 않아 LAN의 정적 파일 요청으로 내려받을 수 없게 한다.

## 15. 완료 조건

1. 서버 PC에서 공용 비밀번호를 설정하고 LAN 사용자는 설정·변경할 수 없다.
2. 일반 사용자는 공개본 외의 문구, 상태, 이력, IP를 API와 화면에서 받지 않는다.
3. 편집자는 이름과 비밀번호로 들어가 모든 페이지의 승인된 콘텐츠 영역을 편집한다.
4. 콘텐츠 수정, 검토, 공개, 공개 취소, 복원이 각각 버전 이력으로 남는다.
5. 이미 공개된 내용을 수정하는 동안 일반 사용자는 마지막 공개본을 계속 본다.
6. 관련 데이터 갱신 시 그 페이지만 자동 생성, 미검토, 비공개로 초기화된다.
7. Weekly Sell-through의 수치는 편집할 수 없고 세부 내용만 편집·공개된다.
8. 동시에 저장해도 조용히 덮어쓰지 않으며 충돌을 명확히 알린다.
9. 런타임 편집과 이력이 Git 상태를 변경하지 않는다.
10. 손상이나 중단 뒤 정상 이력 또는 백업으로 복구하며 복구 불가능하면 안전하게 읽기 전용이 된다.
